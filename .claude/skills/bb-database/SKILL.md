# Book Builder: database

## Ground rules (the user set these)

1. **Never write test data to the user's Neon database.** All experiments, seeds and test
   accounts go into a local throwaway Postgres (see the `bb-verify` skill).
2. **Ask before any production database change.** The user approves each migration
   explicitly ("yes, run the migration"). Approval for one migration doesn't cover the next.
3. **Never print secrets.** Read `DATABASE_URL` from `.env` into a shell variable and print
   only its host, never the whole URL or password.
4. **Don't run `yarn db:push` / `drizzle-kit push` against Neon.** Production changes go
   through reviewed SQL files in `drizzle/manual/`.

## Schema

`src/lib/server/db/schema.ts` (Drizzle, `pg-core`). `auth.schema.ts` is generated by Better
Auth (`yarn auth:schema`) and holds `user`, `session`, `account` and `verification`.

| Table                                 | Key columns                                                                              | Notes                                                                                 |
| ------------------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `book`                                | `user_id`, `title`, `description`, `share_id`                                            | `share_id` is the random id in the public `/read/<shareId>` link; null while private. |
| `part`                                | `book_id`, `user_id`, `has_chapters` (int 1/0), `position`, `status`, `show_description` | A part either holds chapters or holds its own story text.                             |
| `chapter`                             | `part_id`, `position`, `status`, `show_description`                                      | Ownership goes through its part.                                                      |
| `story_text`                          | `content`, `part_id` **or** `chapter_id`                                                 | One row per chapter, or per story-text part.                                          |
| `character`, `system`                 | `user_id`                                                                                | Linked to books through `character_book` and `system_book`.                           |
| `chapter_character`, `part_character` | composite PKs                                                                            | The "cast" of a chapter or part.                                                      |
| `profile`                             | `user_id` PK, `handle` unique, `bio`, `website`, `is_public`                             | The author page at `/author/<handle>`.                                                |

- **Text fields.** Titles are plain text. Descriptions and story text may be rich-text JSON (see the `bb-rich-text` skill), and the server cleans them with `cleanValue` before saving.
- **Status.** `status` is one of `idea`, `outlined`, `drafting`, `revising`, `done` (see `$lib/status.ts`).
- **Ordering.** Sort by `position`, then `createdAt`, then `id`. `bookOutline()` in `$lib/library.ts` does this, so use it rather than re-sorting by hand.
- **`updatedAt`.** It updates itself on writes (`$onUpdate`). Saving story text also marks the chapter (or story-text part), its part and its book as updated in one transaction and returns `touchedAt`; the client then calls `touchLibrary`. See `src/lib/server/story-text.ts`.

## Ownership

Every read and write of a user's data must check ownership:

- **Endpoints** call `requireUser(event)` from `$lib/server/auth-guard`, which throws 401.
- **Records** are looked up with `findOwnedBook` / `findOwnedPart` / `findOwnedChapter` from `$lib/server/ownership`. A miss returns **404**, not 403, so other people's ids can't be probed.
- **Public reading** (`/read/[shareId]`) loads only by `share_id`, with no user, through `readableBook()` in `$lib/server/reading.ts`. Hidden descriptions arrive blank.

## Migrations

Migrations are hand-written SQL in `drizzle/manual/NNNN_short_name.sql`, numbered on from the
last file. `drizzle-kit generate` isn't used. Each file:

- Opens with a comment saying what changes and why, which file it runs after, whether it's safe to run again, and that afterwards `yarn db:push` reports no changes.
- Is a single transaction (`BEGIN; ... COMMIT;`).
- Uses constraint and index names that match what drizzle-kit would generate (`<table>_<column>_<ref table>_<ref column>_fk`, `<table>_<column>_unique`, and the names in `index('...')`). Otherwise drizzle-kit later sees a difference.
- Changes the Drizzle schema in the same commit so code and database agree.
- Lists its column order to match Drizzle's for composite primary keys, e.g. `primaryKey({ columns: [table.characterId, table.chapterId] })`. A different order looks like a change to drizzle-kit (this happened with `chapter_character`).
- Data-only fixes, such as backfilling dates, are fine as migrations too. Say so in the header and make them safe to re-run.

### Prove it on a throwaway database first

1. Start a throwaway Postgres built from the schema **before** your change. The `bb-verify` skill's `scratch-db.sh` builds one from the current schema, so check out the previous commit's `schema.ts`, or build first and change after.
2. Apply the migration: `psql -h localhost -p 54329 -U bb -d bookbuilder -v ON_ERROR_STOP=1 -f drizzle/manual/NNNN_x.sql`.
3. With the new schema in place, run `DATABASE_URL=postgres://bb@localhost:54329/bookbuilder npx drizzle-kit push`. It must report **"No changes detected"**. If it proposes statements, the SQL and the schema disagree. Fix the SQL and repeat.
4. Run the app against the throwaway database and use the feature.

### Applying to Neon, only after the user says yes

```bash
DB=$(grep '^DATABASE_URL=' .env | cut -d= -f2- | tr -d '"')
echo "host: $(echo "$DB" | sed -E 's|.*@([^/:]+).*|\1|')"      # show only the host
psql "$DB" -v ON_ERROR_STOP=1 -f drizzle/manual/NNNN_x.sql
DATABASE_URL="$DB" npx drizzle-kit push 2>&1 | grep -iE "no changes|statements" # verify, don't apply
```

- **psql location.** psql lives in `C:\Program Files\PostgreSQL\18\bin` on this machine. Under Git Bash, quote it as `"/c/Program Files/PostgreSQL/18/bin/psql.exe"`.
- **If drizzle-kit wants changes**, don't confirm anything. Stop and report.
- **Afterwards**, tell the user it was applied and mention the migration file in the commit message ("Migration: drizzle/manual/0006_profiles.sql (already applied to Neon).").

## Seeding test data

- **Where.** Seeds go to the throwaway database only.
- **Rich text.** Rich-text values must be compact JSON that starts exactly with `{"type":"doc"`, so in Python use `json.dumps(doc, separators=(',', ':'))`. JSON with spaces is treated as plain text and shows up raw on the page.
- **Encoding on Windows.** Write SQL as UTF-8 (`PYTHONIOENCODING=utf-8`, `PGCLIENTENCODING=UTF8`). Otherwise curly quotes break the insert.
- **Reserved words.** `user` is a reserved word, so quote it as `"user"`. Passing that through PowerShell loses the quotes, so put SQL in a file and use `psql -f`.
