# Book Builder: database

## Ground rules (the user set these)

1. **Never write test data to the user's Neon database.** All experiments, seeds and test
   accounts go into a local throwaway Postgres (see the `bb-verify` skill). The one exception is
   the public **Demo Author** account (see "The demo account" below), which the user asked for.
2. **Ask before any production database change.** The user approves each migration
   explicitly ("yes, run the migration"). Approval for one migration doesn't cover the next.
3. **Never print secrets.** Read `DATABASE_URL` from `.env` into a shell variable and print
   only its host, never the whole URL or password.
4. **Don't run `yarn db:push` / `drizzle-kit push` against Neon.** Production changes go
   through reviewed SQL files in `drizzle/manual/`.

## Schema

`src/lib/server/db/schema.ts` (Drizzle, `pg-core`). `auth.schema.ts` is generated by Better
Auth (`yarn auth:schema`) and holds `user`, `session`, `account` and `verification`.
`user.email_verified` gates everything: an account that hasn't confirmed its email gets no session
(see "Accounts and email" in the `bb-feature-map` skill). Accounts made before that rule were marked
confirmed by `drizzle/manual/0015_confirmed_accounts.sql`, and a hand-made user (a seed, the demo
account) needs `email_verified = true` to log in. Besides Better Auth's own rows (`reset-password:*`),
`verification` holds the email send counts, `bb-email:*`, which expire with their window. Deleting a
user cascades to everything they own.

- **Headings.** `book.part_labels` and `book.chapter_labels` hold a label style from `$lib/headings`, and `book.chapter_titles` turns chapter titles off in reading mode. `part` and `chapter` each have `heading_label` (null follows the book, `''` hides the label, anything else is the label) and `show_title`.
- **Text fields.** Titles are plain text. Descriptions and story text may be rich-text JSON (see the `bb-rich-text` skill), and the server cleans them with `cleanValue` before saving.
- **Status.** `status` is one of `idea`, `outlined`, `drafting`, `revising`, `done` (see `$lib/status.ts`).
- **Ordering.** Sort by `position`, then `createdAt`, then `id`. `bookOutline()` in `$lib/library.ts` does this, so use it rather than re-sorting by hand.
- **`updatedAt`.** It updates itself on writes (`$onUpdate`). Saving story text also marks the chapter (or story-text part), its part and its book as updated in one transaction and returns `touchedAt`; the client then calls `touchLibrary`. See `src/lib/server/story-text.ts`.
- **Writing days.** The same save also adds the change in word count (new text minus the old) to the writer's `writing_day` row for today, in the same transaction, and returns `writing: { day, delta, today }`. "Today" comes from the `bb-tz` cookie the layout sets from the browser (UTC until it exists). See `src/lib/server/goals.ts` and `$lib/goals.ts`.

- **Series order.** Sort a series with `booksInSeries()` in `$lib/series`. A book's number is its place in that list, not its `series_position`, which can have gaps. On anything public, number the books before leaving out the private ones, so a shared book keeps its real number. Never send a private book's title to a public page: `readerSeries` and `publicSeries` in `$lib/server/series` hold that line.
- **Deleting a book in a series.** `passEntriesOn` moves entries that belong to that book alone onto another book in the series, in the same transaction, so the series' story bible doesn't shrink. The book's delete dialog says so.
- **Entries without foreign keys.** `story_mention` and `entry_link` point at an entry with a type and an id, so nothing cascades when one goes. Anything that deletes an entry must call `forgetEntry` in `$lib/server/bible` first or afterwards in the same transaction: it turns the entry's mentions in the text back into plain words and clears both tables. Deleting a book already does.
- **Mentions on save.** `ownedMentions` drops links to entries the user doesn't own, then `indexMentions` rebuilds the index. An entry mentioned somewhere for the first time joins that chapter's cast and that book. Only the first time, so someone taken out of a cast by hand stays out. The same save casts anyone in the book's story bible whose name is written there for the first time (`castNamed`, comparing against the text before the save), and creating an entry, linking it to a book or changing its name or aliases casts it wherever the book's text newly names it (`castByName`). No table records names: each check reads the text.
- **Versions on save.** A save that changes the text keeps what it replaces in `story_version` when one is due (`keepVersion` in `$lib/server/story-versions`: ten minutes since the last, or a cut of 100 words or more), in the same transaction, and thins the old ones. A restore is a save too and always keeps one. The rules are in `$lib/story-versions.ts`.

## Ownership

Every read and write of a user's data must check ownership:

- **Endpoints** call `requireUser(event)` from `$lib/server/auth-guard`, which throws 401.
- **Records** are looked up with `findOwnedBook` / `findOwnedPart` / `findOwnedChapter` from `$lib/server/ownership`. A miss returns **404**, not 403, so other people's ids can't be probed.
- **Public reading** (`/read/[shareId]`) loads only by `share_id`, with no user, through `readableBook()` in `$lib/server/reading.ts`. Hidden descriptions arrive blank.

## Migrations

Migrations are hand-written SQL in `drizzle/manual/NNNN_short_name.sql`, numbered on from the
last file. `drizzle-kit generate` isn't used. Each file:

- Opens with a comment saying what changes and why, which file it runs after, whether it's safe to run again, and that afterwards `yarn db:push` reports no changes.
- Is a single transaction (`BEGIN; ... COMMIT;`).
- Uses constraint and index names that match what drizzle-kit would generate (`<table>_<column>_<ref table>_<ref column>_fk`, `<table>_<column>_unique`, and the names in `index('...')`). Otherwise drizzle-kit later sees a difference.
- Changes the Drizzle schema in the same commit so code and database agree.
- Lists its column order to match Drizzle's for composite primary keys, e.g. `primaryKey({ columns: [table.characterId, table.chapterId] })`. A different order looks like a change to drizzle-kit (this happened with `chapter_character`). The rule behind it: put a composite key's columns in reverse alphabetical order (`place_id, part_id`, not `part_id, place_id`), or drizzle-kit keeps proposing to drop and re-add the key, even on a database it just built.
- Data-only fixes, such as backfilling dates, are fine as migrations too. Say so in the header and make them safe to re-run.

### Prove it on a throwaway database first

1. Start a throwaway Postgres built from the schema **before** your change. The `bb-verify` skill's `scratch-db.sh` builds one from the current schema, so check out the previous commit's `schema.ts`, or build first and change after.
2. Apply the migration: `psql -h localhost -p 54329 -U bb -d bookbuilder -v ON_ERROR_STOP=1 -f drizzle/manual/NNNN_x.sql`.
3. With the new schema in place, run `DATABASE_URL=postgres://bb@localhost:54329/bookbuilder npx drizzle-kit push`. It must report **"No changes detected"**. If it proposes statements, the SQL and the schema disagree. Fix the SQL and repeat.
4. Run the app against the throwaway database and use the feature.

### Applying to Neon, only after the user says yes

```bash
DB=$(grep '^DATABASE_URL=' .env | cut -d= -f2- | tr -d '"')
echo "host: $(echo "$DB" | sed -E 's|.*@([^/:]+).*|\1|')"      # show only the host
psql "$DB" -v ON_ERROR_STOP=1 -f drizzle/manual/NNNN_x.sql
DATABASE_URL="$DB" npx drizzle-kit push 2>&1 | grep -iE "no changes|statements" # verify, don't apply
```

- **psql location.** psql lives in `C:\Program Files\PostgreSQL\18\bin` on this machine. Under Git Bash, quote it as `"/c/Program Files/PostgreSQL/18/bin/psql.exe"`.
- **Order matters.** Drizzle selects every column in the schema, so code that reads a new column fails on Neon until the migration has run. Apply the migration first, then push the code.
- **If drizzle-kit wants changes**, don't confirm anything. Stop and report.
- **The known false alarm on Neon.** Neon runs Postgres 17, and there drizzle-kit always proposes to drop and re-add five composite keys with the columns they already have: `chapter_character`, `chapter_place`, `part_place`, `chapter_system` and `part_system`. In those tables the key lists its columns in a different order from the table (`PRIMARY KEY (place_id, chapter_id)` on columns `chapter_id, place_id`), and drizzle-kit reads them in table order on 17. Re-adding them changes nothing and it would ask again, so never apply them. Run the check with `</dev/null` so it can't prompt: if those ten statements are all it lists, the database matches. Anything else is a real difference. The local throwaway (Postgres 18) doesn't show this.
- **If that check is blocked.** Claude Code's permission check may refuse `drizzle-kit push` against Neon. Don't retry it or route around it. Read the catalog instead, inside `begin read only;` (`information_schema.columns`, `pg_constraint`, `pg_indexes`), rely on the "No changes detected" from the throwaway database, and say which check ran.
- **Afterwards**, tell the user it was applied and mention the migration file in the commit message ("Migration: drizzle/manual/0006_profiles.sql (already applied to Neon).").

## The demo account (lives in Neon)

A real user named **Demo Author** (handle `demo-author`, email `demo@book-builder.invalid`) lives
in the Neon database so visitors can see a finished book without signing up:

- **Public pages.** `/author/demo-author` lists the book, which is shared at its `/read/<shareId>` link.
- **Content.** It is _The Long Light_ (prologue plus two parts, about 9,800 words, with the statuses
  spread across done, revising, drafting and outlined), the characters Juno Halley, Ade, Pell and
  Tamsin, and the system Starsinging, all from the sample universe in the `bb-homepage` skill.
- **Login.** The password was generated once and saved as `DEMO_AUTHOR_EMAIL` / `DEMO_AUTHOR_PASSWORD`
  in `.env` (gitignored). Never print it. Sign-up is open, so don't rely on the email being unguessable.
- **Rebuilding it.** `scripts/seed-demo-author.mjs`, in this skill's folder, copies _The Long Light_
  from a throwaway database (build one with the `bb-verify` skill and its `seed-long-book.py`) into
  `DATABASE_URL`, replacing the demo user and everything it owns, and sets a new password. Run it
  from the repo root as `node .claude/skills/bb-database/scripts/seed-demo-author.mjs`, with
  `SOURCE_DATABASE_URL`, `DATABASE_URL` and optionally `ENV_FILE` set. Try it on a throwaway target
  first, then run it on Neon only when the user asks. It only ever deletes the one demo user.
- **Don't** use the demo account for experiments. Make a test user on the throwaway database instead.

## Seeding test data

- **Where.** Seeds go to the throwaway database only.
- **Rich text.** Rich-text values must be compact JSON that starts exactly with `{"type":"doc"`, so in Python use `json.dumps(doc, separators=(',', ':'))`. JSON with spaces is treated as plain text and shows up raw on the page.
- **Encoding on Windows.** Write SQL as UTF-8 (`PYTHONIOENCODING=utf-8`, `PGCLIENTENCODING=UTF8`). Otherwise curly quotes break the insert.
- **Reserved words.** `user` is a reserved word, so quote it as `"user"`. Passing that through PowerShell loses the quotes, so put SQL in a file and use `psql -f`.
